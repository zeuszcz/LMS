# Data Model

ERD overview, key tables, indexes, invariants. The full DDL lives in
`backend/alembic/versions/` (autogenerated from `app/models/`).

## Aggregates

```
branch ──< group >── course
              │
              ├──< enrollment >── user (student)
              │
              └──< lesson_instance >── attendance ──< user
                                    │
                                    └──< (Phase 2) assignment >── submission

user ──< user_role
user ──< parent_link >── user (student)

(Phase 2)
subscription ──< lesson_credit_ledger
payment      ──> subscription
invoice      ──> payment   (1C mirror)
```

## Tables (MVP)

### `user`
Identity. Roles via `user_role` link table (many-to-many, branch-scoped).
- `id` UUID PK
- `email` (unique nullable — phone is allowed alone for kids enrolled by parents)
- `phone` (unique nullable, E.164)
- `password_hash` bcrypt
- `full_name`, `locale`, `timezone`
- `is_superuser`
- `last_seen_at`, `disabled_at`, `deleted_at`

### `user_role`
- `(user_id, role, branch_id)` unique
- `role` enum: student/teacher/parent/methodist/branch_manager/admin/b2b_coordinator
- `branch_id` nullable (admin/methodist may be cross-branch)
- `revoked_at` for audit-friendly removal

### `student_profile`, `teacher_profile`, `parent_link`
Role-specific extensions. Always 1:1 with `user`.

### `branch`
20+ rows. `manager_user_id` FK to user.

### `course`
- `language` enum (en/de/fr/it/es/zh/ja/ko)
- `level` CEFR (A1..C2)
- `age_group` (kids/teens/adults)
- `duration_weeks`, `lessons_count`
- `published_at` — null = draft
- (Phase 2) `course_version` — to evolve courses without breaking active groups

### `study_group`
> Renamed from `group` because PostgreSQL reserves `group`.
- `course_id`, `branch_id`, `teacher_id`
- `mode` (offline/online/hybrid)
- `start_date`, `end_date`
- `max_students` default 12
- `status` (planned/active/finished/cancelled)

### `enrollment`
- `(student_id, group_id)` unique among non-deleted
- `enrolled_at`, `left_at`, `placement_score`, `final_grade`

### `lesson_instance`
- `group_id`, `sequence`, `scheduled_at`, `duration_min`
- `actual_started_at`, `actual_ended_at`, `status`
- `notes_for_methodist`

### `attendance`
- PK: `(lesson_instance_id, student_id)`
- `status` (present/late/absent/excused), `participation_score` 1-5
- `recorded_by` FK to teacher

## Indexing strategy

- `lesson_instance(scheduled_at)` btree, partial `WHERE status = 'planned'`
- `attendance(student_id, recorded_at DESC)` for journal queries
- `enrollment(student_id, deleted_at)` partial `WHERE deleted_at IS NULL`
- `notification_outbox(status, scheduled_at)` partial `WHERE status = 'pending'`
- GIN trigram on `course.title`, `course.description` for catalog search
- `audit_log` partitioned by month; retention 24mo

## Hard invariants

1. **`user_role` uniqueness**: a user cannot hold the same role at the same branch twice (excluding revoked).
2. **`enrollment` uniqueness**: a student cannot be enrolled in the same group twice (among non-deleted).
3. **Attendance authority**: `attendance.recorded_by` must be the group's teacher OR a methodist of the group's branch (enforced in service, not DB).
4. **Recording consent**: video session may not start if any participant under 18 lacks an active `recording_consent`. Service-level check.
5. **Idempotent payments**: `payment.idempotency_key` is unique. Webhooks retry safely.
6. **Credit balance non-negative**: `SUM(lesson_credit_ledger.delta)` per subscription must stay ≥ −0.1 × `lessons_included` (small race-tolerance buffer). DB check constraint planned in Phase 2.

## Why these tables and not others

- We **don't** model `room` separately yet — packed into `study_group.room_label` text. Promote to its own table when scheduling collisions become first-class (Phase 2).
- We **don't** version `course` content yet — Phase 2 introduces `course_version`. MVP ships with mutable courses (acceptable since few groups in pilot).
- We **don't** model `payment_method` — it's a YooKassa concern; we store provider ref only.

## Migration discipline

- One concern per migration file.
- Always include reversible `downgrade` (or explicit comment why irreversible).
- Backfills as separate data migrations, not mixed with schema migrations.
- Smoke test: `alembic upgrade head && alembic downgrade -1 && alembic upgrade head` on empty DB before merge.
